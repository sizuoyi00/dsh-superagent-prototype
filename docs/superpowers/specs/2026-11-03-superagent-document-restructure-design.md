# SuperAgent 调研文档重构设计

日期：2026-11-03  
状态：待用户书面评审  
目标读者：同时包含产品、架构和研发角色的混合读者；正文先讲清概念与产品，源码作为实现证据。

## 1. 背景与问题

现有调研已经覆盖 SuperAgent 的产品定位、领域模型、源码调用链、可靠性机制、操作方法和 Multica 对比，事实与证据较完整。但新增内容不断叠加后，文章的阅读顺序失衡：读者先进入 Multica 和函数级调用链，之后才看到领域概念和完整业务流程。

当前主报告约 1,677 行，其中 Multica 专节约占 21.9%，源码调用链约占 31.9%。两部分合计超过全文一半。结果是：

- 主报告的中心从“解释 SuperAgent”偏移到了“罗列实现和竞品细节”；
- Source、Trigger、Mandate、Ticket、Effect、Outbox 等关键概念没有在首次使用前系统解释；
- 业务流程出现得晚，读者难以把函数、状态和产品行为连成一条线；
- 同一机制在多个章节重复说明，句子中的英文术语和源码链接打断阅读；
- 操作手册仍保留早期环境状态，与后续验证结果不一致。

本轮不减少研究深度，而是重新分配信息：主报告负责建立理解，源码负责证明判断，Multica 专题负责承接竞品深挖，操作手册负责可执行步骤。

## 2. 目标与非目标

### 2.1 目标

1. 让没有读过源码的产品或技术读者，可以按顺序理解 SuperAgent 为什么出现、它是什么、怎样工作、当前做到什么程度，以及是否适合采用。
2. 保留完整的关键概念、实际调用流程、底层原理和源码证据，但不让函数名主导叙事。
3. 把 Multica 的版本、调用链、运行实证和案例迁入独立专题；主报告只保留定义、产品、功能、流程和选型层面的对比。
4. 明确三份文档的职责和互链，避免重复维护同一段事实。
5. 修正操作手册中的环境状态，使其与最新验证记录一致。
6. 保留证据等级、版本边界和隐私边界，不把推断写成事实。

### 2.2 非目标

- 不改变 SuperAgent 源码、配置、运行行为或测试逻辑。
- 不新增缺少证据的产品能力，也不把官方设计愿景写成公开原型已经实现的功能。
- 不把主报告改成逐文件源码导读。
- 不把操作手册改写成原理文章。
- 不对 Multica 本机实例执行写操作，也不披露 Workspace、Issue、Task、人员、正文、凭据或仓库标识。
- 不宣称全量测试通过或覆盖率达到 80%。

## 4. 主报告信息架构

主报告按“问题 → 定义 → 产品 → 概念 → 流程 → 原理 → 实现 → 评估 → 对比 → 落地”展开。

### 4.1 执行摘要

用简短段落回答：它是什么、解决什么、当前成熟度如何。开头不堆叠完整术语表和函数名。

### 4.2 为什么需要 SuperAgent

从一个研发协作场景开始：Issue、评论、CI 和 Agent Session 之间需要人持续搬运信息。再归纳五类问题：短命 Session、人工调度、主动性失控、并行上下文污染、失败后难恢复。

### 4.3 定义与边界

区分三个层次：

- SuperAgent 设计思想；
- Router/Worker、事件驱动和授权治理组成的系统架构；
- 当前仓库提供的开源研究原型。

本节同时说明它与 Model、SDK、agent harness/runtime、agent application 和业务工作流的关系，并明确它不是独立基础模型、通用多 Agent SDK 或已验证的托管商业产品。

### 4.4 产品形态与使用方式

说明自托管 DSH bundle、GitHub/飞书入口、管理面板、单仓库部署边界，以及三条用户旅程：

1. 人明确指派任务；
2. 系统依据书面规则发现候选任务；
3. 原 Thread 出现后续评论或状态变化。

安装命令和配置细节统一链接操作手册。

### 4.5 核心概念与领域模型

先给一张领域全景图，再按五组解释：

- 事件与沟通：Source、Trigger、Thread、Channel、Correlation；
- 授权与决策：Policy、Policy version、Gate、Assessment、Decision、Mandate、Scope、Strength、explicit/inferred、off/observe/auto；
- 工作连续性：Ticket、Assignment、Subscription、Input、Report、Attention、Disposition；
- 执行角色：Main Session/Router、Worker Session、execution environment、subagent/job；
- 可靠性：Effect、Outbox、receipt、stable ID、idempotency、retry、backoff、recovery。

重点解释三组容易混淆的关系：Ticket 与 Session、Mandate 与 Prompt、Subscription 与 Correlation。Engine、Passes、SourceContext 等实现词不进入核心业务词汇表。

### 4.6 一项工作如何跑完

先以业务语言完整走一遍主流程：

```text
外部事件
→ Trigger
→ 准入与研判
→ Decision / Mandate
→ Ticket / Assignment
→ Worker 执行
→ Report
→ Effect / Outbox
→ 原会话交付
```

再补充两条分支：主动任务如何从观察转为执行，以及后续评论如何进入已有 Ticket。此处不展开函数级调用栈。

### 4.7 核心设计思想

把现有原则收束为四组：

1. 低注意力的人机协作；
2. 对外保持一个持续 Agent，内部使用多个按任务隔离、可跨轮次恢复的 Session；
3. 用确定性授权约束概率模型；
4. 用事件驱动、状态外置和可靠副作用支持长期运行。

每组都按“解决的问题 → 设计选择 → 代价或边界”解释。

### 4.8 架构与源码实现

源码章节按概念分层，而不是按文件漫游：

1. 宿主与启动：DSH/Cordis 如何装配 bundle，SuperAgent 与 harness/runtime 的边界在哪里；
2. 事件接入：Source 如何生成稳定 Trigger，以及 Source 身份为何是授权信任边界；
3. 决策控制：Gate、Assessment、Decision、Mandate 和 accept 原子事务；
4. 执行隔离：Ticket、Assignment、Worker Session 和工作目录；
5. 模型运行：Prompt 如何组装，工具怎样约束，Session persistence、上下文压缩、subagent/job 如何协作；
6. 可靠交付：Report、Main relay、Effect、Session delivery 和 Outbox；
7. 恢复：幂等、重试、重启和竞态收敛。

每小节统一使用“目的 → 业务例子 → 机制 → 关键源码入口 → 限制”。正文保留一张端到端函数级时序图和一张实现索引表；只有影响语义的分支留在正文。更细的启动、摄取、准入、派发、follow-up、交付、人工操作和恢复链路统一进入主报告的“附录 A：函数级调用链”，不再新建第四份文档，也不只留下无法复核的索引。

### 4.9 可靠性、安全与人工监督

围绕三个实际问题组织：

- 崩溃后会不会丢工作；
- 主动性会不会越权；
- 人怎样发现并介入异常。

保留单机单活、SQLite、Effect/Outbox、凭据、执行权限、pause/stop/retry/reevaluate 和审计边界。

### 4.10 完成度与适用边界

区分“官方文章愿景”“公开原型已实现”“尚未实现或待验证”。合并实验数据、适用场景、不适用场景和生产化缺口。

### 4.11 竞品与 Multica

先以简化市场地图区分 SDK、harness/runtime、coding-agent 产品和协作控制面。市场地图只解释类别，并为每类列 1–2 个代表对象，不再展开全量竞品矩阵。Multica 只保留四层对比：

| 维度 | DSH SuperAgent | Multica |
|---|---|---|
| 定义 | 基于 DSH、面向单仓库持续监听和主动负责的长期 Agent 应用与治理层 | 面向多人、多 Workspace、多异构 Agent 的协作工作区和编排控制面 |
| 产品 | 开源研究原型、自托管 DSH bundle、GitHub/飞书、单仓库边界 | source-available 产品；Cloud、Web、Desktop、自托管、CLI/API，多 Workspace/Project/Agent/Squad |
| 功能 | Source 准入、主动规则、Mandate、单一 Agent 身份、Thread 持续跟进、可靠回复 | 多人协作、Agent 名册、RBAC、Squad、异构 runtime、Issue/Run、Wakeup、Inbox、审阅 |
| 流程 | 事件 → Trigger → Gate/Eval → Mandate/Ticket → Worker → Report/Outbox → 原 Thread | Issue/评论/指派 → Task queue → daemon claim → runtime → timeline/report → review/retry |

正文可保留一个简化案例，但不出现 Multica 数据表、内部函数或逐名词映射。结论统一为：Multica 管理“许多人和许多 Agent 如何在一个工作系统里协作”；SuperAgent 管理“一个 Agent 在什么授权下长期、主动地负责一个仓库”。

### 4.12 试点与落地建议

保留 explicit-only 基线 → inferred observe → 低风险规则 auto 的渐进路径、指标、退出条件和安全底线。这里区分授权强度（explicit/inferred）与接受模式（off/observe/auto），不把它们写成同一枚举。具体命令链接操作手册。

## 7. 写作与证据规则

1. 每节只回答一个主要问题，首段直接给答案。
2. 采用“具体场景 → 概念 → 机制 → 证据”的顺序。
3. 中文术语首次出现时附英文，后文以中文为主；源码标识符保持原样。
4. 一个句子只承载一个主要判断，避免连续堆叠中英文名词。
5. 源码链接放在段末、脚注式证据行或实现索引表，不插入因果句中部。
6. 官方事实由引用支撑，不在每句前重复标签；本地实现结论在段落首次标为“源码观察”；分析判断、推断和待验证内容必须显式标记。来源表继续保留证据等级。
7. 每个核心机制同时回答“解决什么、怎样实现、有什么限制”。
8. 主流程只完整讲一次，其他章节引用对应阶段。
9. 删除模板化过渡语和没有信息量的强调句。
10. 不删除影响正确性的语义：follow-up ownership/handback、context-only Subscription、Mandate 重验、accept 原子事务、Worker report → Main relay → Outbox 两段持久投递、Source 身份信任边界、Effect 与 Outbox 的差异、pause 与 stop 的差异、至少一次交付与非 exactly-once 边界。

## 8. 迁移策略

重构采用“先建立新骨架，再迁移证据，最后去重”的顺序：

1. 为主报告建立新目录和章节职责；
2. 把现有段落按“保留、压缩、迁移、删除重复”分类；
3. 先完成概念和业务流程，再整理源码实现；
4. 将 Multica 深入内容迁入专题，并在主报告保留摘要和链接；
5. 对所有原有关键结论建立迁移清单，避免重写时遗漏；
6. 修订操作手册状态与阅读路线；
7. 连续通读三份文档，消除重复、跳跃和术语不一致。

不直接依赖复制后删除来保证完整性。关键机制和证据将通过章节映射表核对，确保每一项要么保留在主报告，要么迁入专题，要么因重复而明确删除。

## 9. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 压缩源码时丢失关键可靠性语义 | 为授权、follow-up ownership/handback、context-only Subscription、accept 事务、两段持久投递、Source 信任边界、Effect、Outbox、恢复和暂停建立必保清单 |
| 主报告与 Multica 专题重复并逐渐漂移 | 主报告只保留四层摘要；版本和函数细节只有专题维护 |
| 为了顺畅而混淆愿景、实现和推断 | 每节保留证据边界；完成度章节集中说明三者差异 |
| 新源码被错误归因给旧 Multica 二进制 | 专题开头固定三类版本基线，案例逐项标注证据类型 |
| 本机实证泄露敏感信息 | 只保留数量级、目录形态和去标识元数据 |
| 操作手册与报告状态不一致 | 使用同一验证结果表述，并由独立审阅检查 |
| 中文化后失去与源码术语的对应 | 首次出现保留英文，关键对象名不意译源码标识符 |
| 主报告过度压缩，不再满足调用链要求 | 保留业务主流程、函数级主时序和实现索引 |
